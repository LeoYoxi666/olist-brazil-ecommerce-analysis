# Olist 巴西电商平台运营诊断项目：编码与工程要求

本文档将 `编码规范.pdf` 转换为本项目的可执行要求。原 PDF 作为参考原件保留在同一目录。

## 1. 适用范围

- 所有提交到本项目 `src/`、`scripts/`、`tests/` 的 Python 代码必须遵守本要求。
- Notebook 允许用于探索性分析，但一旦逻辑沉淀到可复用函数、数据处理脚本或最终报告流程中，必须按本规范整理。
- 数据分析结论必须能追溯到原始 CSV、清洗规则和计算口径；不得只保留不可复现的手工结果。

## 2. 必须遵守的规则

### 2.1 格式与命名

- 使用 4 个空格缩进，禁止 Tab；单行最大 88 个字符。
- 使用 Black 格式化，顶层函数/类之间空两行，类内方法之间空一行。
- 模块、函数和变量使用蛇形命名；类使用大驼峰；常量使用全大写加下划线。
- 统一使用双引号；多行字符串使用三双引号。
- import 必须按“标准库、第三方库、本地项目”分组，每个 import 独占一行；禁止通配符导入和循环导入。

### 2.2 文档与类型

- 公共模块、类、函数和方法必须有 Google 风格 docstring，说明用途、参数、返回值、异常和必要示例。
- 公共函数的所有参数和返回值必须有类型注解；无返回值明确写 `-> None`。
- 本项目 Python 目标版本为 3.10+，优先使用 `list[str]`、`T | None` 等内置泛型写法。
- 注释解释“为什么这样做”，不复述代码；禁止提交被注释掉的旧代码。

### 2.3 异常、安全与数据访问

- 禁止裸 `except:` 和静默吞掉异常；捕获具体异常并记录上下文，必要时使用 `raise ... from ...`。
- 禁止硬编码密码、Token、密钥和机器专属路径；数据路径通过配置或命令行参数提供。
- 禁止使用 `eval()`、`exec()` 处理外部输入。
- SQL 必须使用参数化查询，禁止字符串拼接 SQL。
- 读取外部文件前检查路径和文件存在性；禁止信任未经校验的外部输入。

### 2.4 函数、模块与性能

- 函数保持单一职责，参数原则上不超过 5 个；不得使用可变对象作为默认参数。
- 单个 Python 文件建议不超过 500 行；模块顶层只做定义，不执行耗时的数据读取或数据库连接。
- 大数据量处理避免不必要的全量复制和循环查询；优先使用向量化操作、分块读取或生成器。
- 原始数据只读保留；清洗结果、分析宽表和最终输出分层存放。

### 2.5 测试与版本控制

- 核心数据清洗、指标计算和业务逻辑必须有单元测试。
- 测试文件放在 `tests/`，文件名和函数名均以 `test_` 开头。
- 每个测试只验证一个场景，按 Arrange-Act-Assert 组织；禁止用 `print` 代替断言。
- 提交信息使用 Conventional Commits，例如 `feat:`、`fix:`、`refactor:`、`docs:`。
- 每次提交聚焦一个功能点，合入前检查业务逻辑、数据口径、安全性和可维护性。

## 3. 本项目目录约定

```text
olist_brazil_ecommerce/
├─ data/
│  ├─ raw/              原始 CSV，只读，不覆盖
│  └─ processed/        清洗后的表和分析宽表
├─ docs/
│  └─ reference/        项目 PDF、编码规范和数据说明
├─ notebooks/           探索性分析，按编号排列
├─ src/                 可复用的数据处理和分析模块
├─ scripts/             可重复执行的入口脚本
├─ tests/               单元测试与集成测试
├─ configs/              配置文件，不放敏感信息
├─ outputs/             图表、看板和报告
├─ pyproject.toml       Black、isort、flake8、mypy 配置
├─ requirements.txt     项目依赖
├─ README.md            项目说明
└─ .gitignore
```

PDF 中的 API、service、DAO 层主要适用于应用服务。本项目是离线数据分析项目，不强行建立这些空层；相应地，用 `src`、`scripts`、`notebooks`、`tests` 和 `data` 层表达数据分析流程。

## 4. Olist 项目专属数据要求

- `customer_unique_id` 是用户分析主身份，不能用 `customer_id` 直接计算复购。
- `order_items`、`payments`、`reviews` 与订单均可能一对多；必须先按订单聚合，再合并到订单级表，防止金额重复。
- `geolocation` 先去重/聚合后再关联邮编，避免一对多连接放大订单量。
- 原始金额、订单状态和时间字段保持原始值，同时在处理层生成清晰命名的衍生字段。
- GMV、完成订单、客单价、复购率、配送时长和延迟率必须在项目文档中注明定义；没有成本数据时不得把代理指标表述为真实利润。
